B. Existing AI/ML and security functionality

Existing LLM agent

backend/app/services/agent.py defines AgentService.

  • Uses OpenAI structured output when an API key is configured.
  • Hardcodes model="gpt-4o" in _call_openai_structured().
  • Defines OPENAI_MODEL in configuration, but the agent does not use that setting.
  • Extracts recipient, ETH amount, and explanation.
  • Validates the result through AgentProposalRequest.
  • Falls back to regex parsing if OpenAI fails or is unavailable.

The fallback parser extracts an address and amount, then falls back to a generic number and ultimately a default 0.01 ETH amount. This is bounded later by policy, but ambiguous extraction is not itself fail-closed.

Existing validation

backend/app/schemas/__init__.py defines:

  • AgentProposalRequest — prompt, recipient, amount, chain, and asset validation.
  • NormalizedAction — canonical action representation for policy, token, and signer code.
  • PolicyDecisionType — ALLOW, ESCALATE, and BLOCK.

Existing policy engine

backend/app/services/policy_engine.py defines a pure deterministic PolicyEngine.evaluate() function. It checks asset type, chain, blocked recipients, allowlists, per-transaction limits, daily limits, and escalation thresholds.

Its decision priority is:

BLOCK > ESCALATE > ALLOW

There is no transaction risk score, recipient-novelty feature, ML prediction, or model-based security decision.

Existing capability and signer controls

  • capability.py issues short-lived HS256 JWT capability tokens.
  • signer.py independently verifies token claims and transaction parameters.
  • The signer checks chain ID, recipient, amount, digest, proposal ID, active policy version, expiry, and replay state.
  • The private key is loaded only within the signer implementation.

Existing audit and logging

  • audit.py sanitizes details and maintains a hash chain.
  • logging.py redacts configured sensitive field names.
  • The agent and proposal routes still log truncated prompt text. This is not a private-key leak, but it can expose sensitive invoice, email, or external-message content.

C. Prompt-injection defenses and verified gaps

What exists

The repository defends primarily against the consequences of malicious model output:

  • Pydantic validation;
  • deterministic policy evaluation;
  • recipient allowlists and blocklists;
  • amount and daily spending limits;
  • human approval for escalated actions;
  • action-bound capability tokens;
  • independent signer verification;
  • replay protection.

What does not exist

There is no prompt-injection detector. The existing test_prompt_injection.py verifies that malicious prompts cannot bypass policy; it does not classify or screen text.

Missing attack coverage includes:

  • indirect injection in invoices or webpages;
  • hidden instructions embedded in otherwise benign text;
  • Unicode, whitespace, and encoding obfuscation;
  • multilingual attacks;
  • fake system: or developer: messages;
  • secret-exfiltration requests;
  • address-substitution instructions;
  • benign text containing security terminology;
  • detector timeout and malformed-result behavior;
  • disagreement between a detector and the policy engine.

D. Security flow and authority boundaries

  ↓
AgentPromptRequest
  ↓

  ↓
AgentProposalRequest validation
  ↓
Proposal stored as PROPOSED
  ↓
POST /api/v1/proposals/{id}/evaluate
  ↓
NormalizedAction
  ↓
PolicyEngine.evaluate()
  ↓
ALLOW / ESCALATE / BLOCK
  ↓
Human approval if required
  ↓
CapabilityService.issue_token()
  ↓
IsolatedSigner.sign_transaction()
  ↓
BlockchainService.submit_raw_transaction()

The deterministic policy engine is authoritative for policy decisions. The signer is authoritative for final signing authorization. The LLM and any future AI/ML detector must remain untrusted.

Required invariant: an AI/ML score may increase scrutiny, escalate, or block an action. It must never convert a policy denial into approval, issue a capability token, or authorize signing independently.

Any future detector failure, timeout, invalid output, or ambiguous result should fail closed into escalation or blocking, depending on the agreed contract.

ModernBERT is an encoder architecture intended for classification and other language tasks, with documented long-context support up to 8192 tokens. That does not establish prompt-injection accuracy for KiteShield. A labelled benchmark is required. References: ModernBERT paper and Hugging Face documentation.

jevos is an open-source local alternative designed for CPU inference and yes/no decisions. Its upstream latency and accuracy numbers are not KiteShield measurements. The hosted Jev API is a separate cloud service with network, privacy, and cost implications.

A local Jev-style model should return only an advisory probability. It must not become the authorization authority.

F. Testing and data findings

The repository uses pytest, pytest-asyncio, pytest-cov, Ruff, and mypy. It does not currently depend on Hypothesis, Transformers, PyTorch, ONNX Runtime, OpenVINO, or model-serving libraries.

There is no labelled prompt-injection dataset or ML evaluation harness. Existing database entities include proposals, policy decisions, approvals, transactions, capability tokens, audit events, and spending records, but they do not contain ground-truth injection or fraud labels.

Recommended evaluation data

BENIGN:
- normal invoices and ordinary payment instructions
- policy explanations
- quoted text mentioning security terminology

MALICIOUS:
- direct instruction override
- indirect invoice/webpage injection
- secret exfiltration
- address substitution
- policy bypass
- tool/action redirection

ADVERSARIAL:
- paraphrases
- Unicode and whitespace obfuscation
- multilingual variants
- long benign prefixes
- fake role markers
- HTML/Markdown embedding
- attacks split across fields

Required metrics

  • malicious-class precision, recall, and F1;
  • macro F1;
  • false-positive rate on benign operational text;
  • false-negative rate on adversarial examples;
  • p50 and p95 inference latency;
  • threshold and calibration analysis;
  • failure and timeout rates;
  • regression tests proving policy BLOCK remains terminal.

No accuracy or latency claim should be made until this evaluation exists.

H. Phased implementation plan

Phase 1 — Contract and deterministic baseline

  • Agree on input source types: user, invoice, webpage, email, and tool output.
  • Agree on labels, score semantics, and failure behavior.
  • Implement a pure rule-based detector.
  • Add unit tests for benign, direct, indirect, obfuscated, and malformed inputs.
  • Do not touch policy, signer, database, or API routes yet.

Phase 2 — Boundary integration

  • Screen external text before the LLM receives it.
  • Preserve detector metadata as an advisory safety signal.
  • Record only rule IDs, label, score, and model version.
  • Do not log raw external documents by default.

Phase 3 — Deterministic transaction-risk baseline

  • Add amount, recipient novelty, velocity, policy flags, and injection signals.
  • Return an advisory risk result.
  • Allow risk to escalate or block, never weaken a policy denial.

Phase 4 — Evaluation harness

  • Add versioned labelled fixtures.
  • Add threshold sweeps and latency measurements.
  • Add adversarial regression tests.
  • Measure the baseline before considering ML.

Phase 5 — Optional model benchmark

  • Benchmark DistilBERT and ModernBERT locally.
  • Benchmark jevos as a supplementary yes/no signal.
  • Compare every candidate against the rule baseline.
  • Adopt a model only if recall improves without unacceptable false positives or latency.

Freeze the AI/ML detector contract with the team and implement the deterministic baseline as an isolated package.
